# TDD 컨벤션

코드 변경이 필요한 작업은 기본적으로 RED -> GREEN -> REFACTOR 순서로 진행한다. 이 문서는 "항상 테스트를 많이 쓰라"가 아니라, 변경 이유를 먼저 검증 가능한 형태로 고정하기 위한 기준이다.

## 1. 기본 루프

### RED

먼저 실패하는 테스트를 작성하거나 기존 테스트로 실패를 재현한다.

- 버그 수정: 버그를 재현하는 테스트를 먼저 만든다.
- 기능 추가: 새 동작을 설명하는 테스트를 먼저 만든다.
- 리팩터링: 기존 테스트가 현재 동작을 보호하는지 먼저 확인한다.

### GREEN

테스트를 통과시키는 최소 구현만 한다.

- 실패한 테스트가 요구하는 범위를 넘겨 구현하지 않는다.
- 미래에 필요할 것 같은 옵션, 추상화, 예외 처리는 넣지 않는다.
- 통과를 위해 테스트를 느슨하게 바꾸거나 삭제하지 않는다.

### REFACTOR

테스트가 통과하는 상태에서만 구조를 정리한다.

- 중복 제거, 이름 정리, 책임 분리는 이 단계에서 한다.
- 파일 위치와 책임 분리는 `folder-structure.md`와 `architecture-convention.md`를 따른다.
- 리팩터링 뒤에도 같은 테스트가 통과해야 한다.

## 2. 적용 대상

다음 작업은 TDD 루프를 기본값으로 둔다.

- 버그 수정
- 기능 추가
- 동작이 바뀌는 리팩터링
- 순수 로직, API 함수, hook, 컴포넌트 동작 변경
- 회귀 가능성이 있는 조건 분기 변경

## 3. 예외

아래 작업은 테스트를 먼저 쓰지 않아도 된다.

- 문서 수정
- 단순 스타일 수치 조정
- import 경로 정리
- 파일명 변경
- 타입 이름 변경처럼 런타임 동작이 바뀌지 않는 변경
- 테스트 비용이 변경 위험보다 명확히 큰 단순 수정

예외를 적용하면 작업 설명이나 최종 보고에 이유를 짧게 남긴다.

## 4. 테스트 위치

테스트 파일 위치와 이름은 `folder-structure.md`의 테스트 규칙을 따른다.

- 컴포넌트: 대상 컴포넌트 옆의 `{Name}.test.tsx`
- API, hook, lib, util: 대상 파일 옆의 `{name}.test.ts`
- E2E: `e2e/`

## 5. 검증 명령

작업 범위에 맞는 가장 작은 검증부터 실행한다.

- 단일 테스트가 가능하면 해당 테스트만 먼저 실행한다.
- 관련 테스트가 통과하면 필요에 따라 `npm run test`로 넓힌다.
- 구조 변경이 있으면 `npm run fsd`를 실행한다.
- 최종 확인이 필요하면 `npm run lint`, `npm run build`를 실행한다.
