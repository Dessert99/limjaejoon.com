# TDD 컨벤션

코드 변경이 필요한 작업은 기본적으로 RED -> GREEN -> REFACTOR 순서로 진행한다. 루프 자체는 일반적인 TDD와 같으므로 여기서 다시 설명하지 않는다. 이 문서는 "항상 테스트를 많이 쓰라"가 아니라, **무엇을 테스트하지 않을지**를 정하는 기준이다.

테스트 파일 위치와 이름은 `folder-structure.md` 5절을 따른다.

## 1. 예외

아래 작업은 테스트를 먼저 쓰지 않아도 된다.

- 문서 수정
- 단순 스타일 수치 조정
- import 경로 정리
- 파일명 변경
- 타입 이름 변경처럼 런타임 동작이 바뀌지 않는 변경
- 테스트 비용이 변경 위험보다 명확히 큰 단순 수정

예외를 적용하면 작업 설명이나 최종 보고에 이유를 짧게 남긴다.

## 2. 테스트 설명

`describe`·`it`의 설명문은 한국어로 쓴다. 컴포넌트명·prop·`ref` 같은 고유 식별자는 원문(영문) 그대로 두되, 문장은 한국어로 동작을 서술한다.

설명에는 구현 방식이 아니라 관찰 가능한 동작을 적는다.

## 3. 테스트 가치 기준

테스트는 "코드가 존재한다"가 아니라 "깨지면 사용자가 겪을 계약이 깨진다"를 증명해야 한다.

- 외부 라이브러리가 이미 보장하는 동작은 반복 검증하지 않는다.
- 우리 코드가 추가한 분기, 계산, 조립, props 전달, ref 전달, 접근성 배선만 검증한다.
- 실패했을 때 원인이 우리 코드인지 라이브러리 내부인지 애매한 테스트는 피한다.
- 단순 렌더 스모크 테스트는 public API가 깨지는 비용이 큰 shared 레이어에서만 제한적으로 둔다.
- `className` 병합 테스트는 소비자가 레이아웃·상태 스타일을 덧입히는 public 계약일 때만 둔다.
