# 홈 섹션 1 설계 — 소개 화면과 장면 배경 (Intro Section & Scene Backdrop)

> **구현은 별도 플랜에서 진행한다.** 이 문서는 브레인스토밍으로 확정한 설계를 자족적으로 옮긴 스펙이다. 홈 전체가 아니라 **첫 섹션 하나**와 그것이 요구하는 배경 위젯에 한정한다.

## 배경

리테마([2026-07-25 스펙](2026-07-25-design-system-terracotta-retheme-design.md))로 디자인 언어는 완성됐으나, 페이지는 아직 옛 뼈대다. 홈은 현재 `Hero + Skills + Projects`라는 관습적 포트폴리오 배치이고, 사용자는 이를 전면 폐기하기로 했다.

새 홈의 정체성은 **"나라는 사람을 각인시키는 공간"** 이다. 첫인상에서 "와!" 가 나오고, 표면은 간결하되 더 알고 싶으면 클릭해 깊어진다. 흔히 말하는 포트폴리오 양식(히어로 → 스킬 → 프로젝트 → 연락처)을 의도적으로 쓰지 않는다.

## 목표

- 홈을 **섹션 단위로 걸리는 풀페이지 스크롤**로 재구성하고, 그 첫 섹션을 완성한다.
- 프라하 도시 실루엣을 **코드로 그린 레이어**로 세우고, 스크롤에 비례해 좌 → 우로 흘려 깊이감을 만든다.
- GSAP을 이 레포에 처음 도입하면서, **사용자가 직접 읽고 튜닝할 수 있는** 파일 경계를 확립한다.

## 비목표 (범위 밖 / 후속)

- **섹션 2 이후** — 강가(카를교에서 본 프라하 성) 장면, 경력·프로젝트·기술 스택 섹션. 장면 데이터 구조는 섹션 2를 수용하도록 설계하되, 이번에 만들지 않는다.
- **섹션 간 `snap`** — 섹션이 하나뿐이라 붙을 대상이 없다. 섹션 2 도입 시 `pages/home`에 스크롤 오케스트레이션으로 추가한다.
- **회고·생각 콘텐츠 시스템** — 저장소·작성 경로·라우트가 필요한 별도 하위 프로젝트. 홈에 진입점만 언젠가 생긴다.
- **사이트 지도 재편** — docs 페이지 신설, 랩과 docs의 경계, 헤더·사이드바 재설계. 사용자가 전면 재구성 예정이라 이 스펙은 관여하지 않는다.
- **실제 콘텐츠** — 소개 문구, 이미지, 경력 항목의 내용. 구조가 정해진 뒤 채운다.
- **실사 사진** — 채택하지 않는다. 근거는 리테마 스펙의 2026-07-26 정정 참고.

## 확정 결정 (브레인스토밍)

1. **홈 구조 = 섹션 단위 풀페이지 스크롤.** 자유 스크롤이 아니라 화면마다 섹션이 걸린다. GSAP ScrollTrigger `pin`.
2. **섹션 1 = 소개 화면.** 프라하 도시 실루엣 배경, 화면 중앙 높이에 좌측 정렬된 소개 문구, 우측 이미지 자리.
3. **배경만 움직인다.** 문구와 이미지는 고정. 배경은 좌 → 우 수평 이동.
4. **이동 드라이버 = 스크롤 진행도.** 자동 재생이 아니다. "걸어서 강가에 도착한다"는 서사가 섹션 2 전환과 맞물리고, 무한 루프 이음매 문제가 없다.
5. **실루엣 구성 = 지붕선 3겹 + 첨탑·돔.** 지붕선만으로는 장소가 특정되지 않고, 가스등 발광은 AI티 배제 원칙과 결이 가까워 채택하지 않는다.
6. **배경은 섹션마다 다른 장면.** 홈 전체를 덮는 단일 배경이 아니다. 따라서 데이터는 **장면(scene) 단위**로 묶는다.
7. **모바일도 핀 유지.** 방문의 상당수가 모바일이므로 핵심 연출을 빼지 않는다. 배경은 새로 만들지 않고 **같은 장면, 다른 크롭과 강도**로 대응한다.
8. **`gsap.matchMedia()`로 반응형과 reduced-motion을 통합**한다. 별도 `useReducedMotion` 훅은 만들지 않는다.

## 섹션 1 레이아웃

화면 높이는 `100dvh`. 모바일 주소창이 스크롤 중 접혔다 펴지며 `100vh`가 튀는 문제를 피한다.

| 요소 | 배치 | 비고 |
|---|---|---|
| `FRONTEND` 라벨 | 좌측 상단 | 자간 넓은 소형 대문자, `clay` 계열 강조 1회 |
| 이름 | 좌측, 라벨 아래 | 화면에서 가장 큰 활자 |
| 소개 문구 | 좌측, 이름 아래 | 여러 줄 |
| 이미지 | 우측 | 이번엔 자리만 확보 |
| 실루엣 배경 | 하단 약 1/3 | 텍스트 영역과 겹치지 않는다 |
| 스크롤 힌트 | 하단 중앙 | 최소 크기 |

**비대칭 배치인 이유:** 정중앙 대칭 배치는 관습적 포트폴리오의 지문이다. 좌측 문구 / 우측 이미지로 밀면 시선이 왼쪽에서 오른쪽으로 흐르는데, 이는 **배경이 흐르는 방향과 같은 축**이라 레이아웃과 연출이 서로를 보강한다.

**하늘은 단색이다.** 황혼을 그라데이션으로 표현하면 배제하기로 한 AI티가 그대로 나온다. 대신 겹마다 명도·채도를 낮춰 공기원근을 만든다 — 먼 겹일수록 어둡고 탁하다.

## 장면 데이터 모델

사용자가 가장 자주 만질 지점이므로 형태를 스펙에 고정한다. 장면 하나는 겹의 배열이고, 겹 하나는 다음 항목을 갖는다.

| 필드 | 뜻 | 예 |
|---|---|---|
| `id` | 겹 식별자 | `far` / `mid` / `near` |
| `depth` | 이동 비율. `0`이면 고정, `1`이면 스크롤과 동속 | `0.2` |
| `path` | SVG 지붕선 좌표 | `'M0,480 L0,345 …'` |
| `tone` | 색 **역할** (값이 아니다) | `far` / `mid` / `near` |
| `hideOnMobile` | 모바일에서 생략 여부 | `true` |

**`tone`이 값이 아니라 역할인 이유:** 데이터에 `#46423B` 같은 값을 박으면 라이트 모드에서 따라오지 않는다. 역할만 적고 실제 색은 `.css.ts`가 토큰에서 매핑하면, 대낮 프라하로 뒤집는 일이 토큰 교체로 끝난다. 어제 도입한 `no-raw-design-values` 규칙과도 어긋나지 않는다.

이 모델의 결과로 **겹 추가 = 배열 항목 하나**, **깊이 조절 = 숫자 하나**, **색 조정 = 매핑 한 줄**이 된다.

## 파일 구조와 책임

원칙은 하나다 — **GSAP을 아는 파일은 하나뿐이다.** 나머지는 평범한 React·SVG여서 GSAP을 몰라도 읽고 고칠 수 있어야 한다.

```
src/widgets/scene-backdrop/
├── config/
│   └── scenes.ts                  장면·레이어 데이터
├── model/
│   ├── types.ts                   Scene·SceneLayer 타입 계약
│   └── useHorizontalParallax.ts   GSAP을 아는 유일한 파일
├── ui/
│   ├── SceneLayer/                SVG 한 겹 렌더 (순수)
│   └── SceneBackdrop/             장면 조립 + 훅 연결
└── index.ts

src/pages/home/ui/IntroSection/    소개 문구 + 이미지
```

| 파일 | 책임 | GSAP 의존 |
|---|---|---|
| `config/scenes.ts` | 겹의 개수·모양·깊이 | 없음 |
| `model/types.ts` | 데이터 계약 | 없음 |
| `model/useHorizontalParallax.ts` | 스크롤 → 수평 이동, 반응형·reduced-motion 분기 | **유일** |
| `ui/SceneLayer` | 겹 하나를 SVG로 그린다 | 없음 |
| `ui/SceneBackdrop` | 장면을 조립하고 훅을 연결한다 | 없음 |
| `pages/home/ui/IntroSection` | 문구·이미지 배치 | 없음 |

**widget 레이어인 이유:** 섹션 2가 같은 메커니즘에 장면만 다르다. 페이지에 묶으면 섹션 2에서 복제하게 된다. 독립적으로 완결된 UI 블록이므로 widget이 맞다.

`SceneBackdrop`과 `useHorizontalParallax`는 클라이언트 컴포넌트다. `'use client'` 누락은 vitest·tsc가 잡지 못하고 `npm run build`에서만 드러난다.

## GSAP 규약

- **진입점은 `src/shared/lib/gsap/index.ts` 하나다.** 컴포넌트에서 `import gsap from 'gsap'` 을 직접 하지 않는다. 플러그인 등록이 한 곳에 모인다. ScrollTrigger 등록도 여기에 추가한다.
- **모션 권한 경계** — 스크롤 연동·타임라인·물리 연출만 GSAP이 맡는다. 상태 전이(hover·press·open/close)는 기존 CSS `transition` + `vars.motion` 그대로다. 선을 긋지 않으면 같은 움직임의 출처를 추적할 수 없게 된다.
- **이징 상수 공유는 이번에 하지 않는다.** `vars.motion.easing.spring` 이 CSS `cubic-bezier` 문자열이라 GSAP `ease` 에 넣을 수 없다는 사실은 유효하나, 섹션 1은 스크롤 진행도에 선형으로 묶이는 `scrub` 이라 이징 자체가 없다. 실제로 이징이 필요한 연출이 나올 때 순수 TS 상수로 추출한다.
- **브레이크포인트는 `shared/styles/breakpoints.ts` 의 `bp` 를 단일 소스로 쓴다.** CSS는 768인데 GSAP은 767.5인 식의 어긋남은 원인 추적이 매우 어렵다.

## 반응형과 접근성

반응형이 **두 층으로 갈린다**는 점이 GSAP 도입에서 가장 먼저 걸리는 함정이다.

- **CSS 층** — 문구 크기, 이미지 배치, 여백, SVG 크롭 지점. 기존 sprinkles 브레이크포인트 그대로.
- **JS 층** — 수평 이동 거리, 겹 표시 여부, `pin` 설정. `.css.ts` 에 미디어쿼리를 아무리 써도 GSAP이 인라인으로 박는 transform 값은 바뀌지 않으므로 `gsap.matchMedia()` 에서 분기한다.

모바일 대응은 **배경을 새로 만들지 않고** 같은 장면에 다음 세 가지만 다르게 준다: `viewBox`·`preserveAspectRatio` 로 크롭 지점 조정, `hideOnMobile` 로 겹 생략, 수평 이동 거리를 화면폭 비례로 산출. 두 벌을 유지하면 튜닝할 때마다 두 번 고쳐야 한다.

`prefers-reduced-motion: reduce` 에서는 **수평 이동을 걸지 않는다.** 실루엣은 정지 상태로 렌더된다. 이 분기는 `matchMedia()` 조건으로 다른 브레이크포인트와 같은 자리에서 처리한다.

## 테스트 전략

[tdd-convention.md](../../conventions/tdd-convention.md) 3절을 그대로 적용한다. 예외가 아니라 규칙의 정상 적용이다.

**검증하지 않는 것:** 애니메이션의 실제 결과. jsdom에는 레이아웃 엔진이 없어 `getBoundingClientRect()` 가 전부 0을 반환하므로 이동을 관찰할 수 없다. 관찰할 수 없으면 남는 선택지는 `expect(gsap.to).toHaveBeenCalled()` 같은 구현 받아쓰기뿐이고, 이는 구현을 바꾸면 동작이 같아도 깨지고 동작이 망가져도 호출만 맞으면 통과한다. `useGSAP` 의 자동 cleanup도 라이브러리가 보장하는 영역이라 검증하지 않는다.

**검증하는 것:**

- `matchMedia` 분기 — reduced-motion과 모바일 조건에서 수평 이동이 걸리지 않는지
- 순수 계산 — `depth` 와 스크롤 진행도로 이동량을 산출하는 함수
- 조립 — 장면 데이터의 겹 개수만큼 SVG가 렌더되는지, `hideOnMobile` 겹이 빠지는지

실제 움직임은 브라우저에서 육안으로 확인한다. 스크롤 감각과 깊이감은 어떤 단위 테스트도 대신할 수 없다.

## 회귀 영향

- **기존 홈 3섹션(`HeroSection`·`SkillsSection`·`ProjectsSection`)은 폐기 대상**이다. 다만 섹션 1만 만드는 이번 범위에서 전부 지우면 홈이 빈 화면이 된다. 삭제 시점은 구현 플랜에서 정한다.
- `entities/profile` 의 `name` 필드에 `'나무가 아닌 숲을 보는 개발자 임재준'` 처럼 수식어가 들어가 있다. 새 레이아웃은 라벨·이름·문구를 분리해 놓으므로 데이터 모델 조정이 따라온다.
- ScrollTrigger 도입으로 `shared/lib/gsap/index.ts` 의 플러그인 등록이 늘어난다.

## 알려진 사각지대

`no-raw-design-values` 규칙은 `.css.ts` 만 커버한다. GSAP은 JS로 인라인 스타일을 쓰므로 이 울타리 밖이며, 파랄랙스 코드에서 raw 값이 다시 샐 수 있다. 이번에 규칙을 확장하지는 않되, `useHorizontalParallax` 의 수치는 전부 `config/scenes.ts` 와 `bp` 에서 오도록 해 사실상 같은 규율을 지킨다.

## 열린 질문

- docs 페이지와 랩의 경계, 회고의 위치, 헤더·사이드바 재설계는 별도 논의 대상이다.
