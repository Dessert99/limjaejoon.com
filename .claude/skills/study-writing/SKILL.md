---
name: study-writing
description: 기술 개념을 학습용으로 설명하거나 블로그 글 초안을 쓸 때 따르는 글쓰기 규칙. 1차 자료로 사실을 확인하고, 문장마다 번호를 붙여 단계적으로 쌓아 쓰며, 해라체와 고정된 출력 포맷을 지킨다. 사용자가 "공부하게 정리해줘", "학습용으로 정리", "블로그 글로 써줘", "study-writing" 같은 말로 기술 개념을 학습 글로 정리해 달라고 할 때 쓴다. 코딩 중에 나온 일반 질문에 답할 때는 쓰지 않는다.
---

학습 글은 아래 규칙을 따른다. 작업 진행이나 반영 결과를 채팅으로 보고할 때는 [출력 포맷]을 따르지 않는다.

[정리 위치]
- 정리한 글은 사용자가 주는 노션 링크의 페이지에 쓴다.
- 링크를 받기 전에는 노션 페이지를 새로 만들지 않고, 사용자에게 링크를 요청한다.


[작업 순서]
- 1차 자료를 확인한 뒤 초안을 scratchpad의 이번 글 전용 폴더(`study-writing-<YYYYMMDD-HHMM>/`)에 마크다운 파일로 쓴다. 노션에는 아직 쓰지 않는다.
- 초안을 Codex에게 넘겨 피드백을 받는다. 반영한 뒤 같은 초안을 다시 넘기지 않는다. ChatGPT 구독의 사용량 한도 때문이다.
- 사용자 피드백으로 구조를 크게 바꿨을 때는 노션에 쓰기 전에 고친 본문을 Codex에게 한 번 더 넘긴다. 소제목을 더하거나 빼거나 순서를 바꾼 경우, 한 소제목의 절반 이상을 새로 쓴 경우가 여기에 해당한다.
- 지적마다 반영과 보류를 정한다. 사실 지적은 1차 자료로 다시 확인한 뒤 반영하고, 근거가 약하거나 취향 차이인 지적은 보류한다.
- 문체와 출력 포맷은 Codex에게 맡기지 않고, 이 스킬 규칙과 대조해 직접 점검한다.
- 노션에 쓰기 전에 소제목 사이에 서로 어긋나는 문장이 없는지 훑는다.
- 최종본을 노션에 한 번에 쓰고, 이번 글 전용 폴더를 지운다.
- 채팅에는 반영한 지적과 보류한 지적을 이유와 함께 짧게 보고한다.
- Codex 실행이 실패하면(로그아웃, 네트워크) 피드백 없이 진행하고, 보고에 그 사실을 적는다.
- 사용자가 노션 본문 중간에 남긴 피드백 블록은 하나씩 반영하고, 반영한 블록은 지운다. 반영하지 않은 블록이 있으면 이유를 보고한다.
- 사용자 피드백으로 고칠 때도 새로 쓰거나 바꾼 문장은 1차 자료로 다시 확인한다. 정확성에 필요한 문장을 지우라는 요청을 받으면, 지우기 전에 이유를 말하고 더 분명한 문장을 제안한다.


[Codex 피드백]
- 프롬프트 파일에 아래 지시, 제목, 초안을 차례로 넣고, 저장소 루트에서 읽기 전용으로 실행한다.
    ```sh
    codex exec -s read-only --ephemeral -o <폴더>/codex.md - < <폴더>/prompt.md
    ```
- 프롬프트 지시는 아래 내용을 그대로 쓴다. 스킬 전체는 넘기지 않는다. 문체 지적이 섞이면 사실 지적이 묻히기 때문이다.
    ```text
    너는 기술 학습 글의 검토자다. 아래 초안을 다음 세 관점에서만 검토한다.
    1. 사실 정확성: 틀린 주장, 지나친 일반화, 특정 버전에서만 맞는 내용. 코드 예제가 글에 적힌 대로 동작하는지(출력 내용, 순서, 시점).
    2. 처음 배우는 사람의 흐름: 설명 없이 나온 용어, 문장이나 소제목 사이의 비약, 앞에서 세우지 않은 개념에 기대는 문장.
    3. 범위: 제목의 질문을 이해하는 데 빠진 핵심 단계, 질문과 상관없이 깊어진 곁가지.
    문체, 맞춤법, 출력 포맷은 지적하지 않는다. 글을 고쳐 쓰지 않는다.
    지적마다 위치(소제목, 번호), 문제, 근거, 고칠 방향, 확신도(높음/중간/낮음)를 적는다.
    문제가 없으면 "지적 없음"이라고만 답한다.
    ```


[제목과 설명]
- 제목은 노션 페이지 제목으로 쓴다. 검색어 + 글이 답하는 내용 순서로, 기술 이름을 앞에 두고 35자 안팎으로 쓴다.
    - 예) Next.js 하이드레이션(Hydration) 원리: renderToString부터 hydrateRoot까지
- 설명은 페이지 본문 맨 위에 인용 블록(`>`)으로 넣고, 글의 결론을 미리 말한다. 제목이 질문이면 그 답을, 개념 소개면 그 개념의 정의를 쓴다.
- 설명은 본문이 받쳐 주는 범위까지만 쓰고, 결론에 붙는 조건은 빼지 않는다.
- 글이 다루는 라이브러리나 도구의 공식 사이트와 저장소 링크는 그것을 소개하는 소제목 바로 아래에 넣는다. 링크 글자는 "공식 사이트", "GitHub"처럼 줄이지 않고 전체 URL을 그대로 보이게 쓴다. 이 줄에는 번호를 붙이지 않는다.
    - 예) https://github.com/47ng/nuqs
- 설명에는 「~를 다룬다」, 「~를 정리한다」, 「~를 기준으로」 같은 범위·기준 소개를 쓰지 않는다.
    - 예) Zod는 TypeScript 타입이 사라지는 런타임에 외부 데이터를 스키마로 검증하는 라이브러리다.


[글 구성]
- 정의에서 출발해, 그 정의를 이해하는 데 필요한 개념을 하나씩 엮으며 단계적으로 쌓아 간다.
- 소제목은 앞 소제목에서 생긴 질문에 답하는 순서로 놓는다.
- 주장에 이유를 댈 때는 자료나 소스에서 확인한 한 층 아래의 구조로 받친다. 이유를 확인하지 못했으면 지어내지 않고 확인하지 못했다고 밝힌다. 예) "한 번에 하나만 실행한다"는 콜 스택이 하나이고 맨 위만 실행된다는 구조로 받친다.
- 성질의 결과(보장과 대가)와 흔한 오개념은 1차 자료나 실제 동작으로 확인되는 것만 쓴다. 확인되는 것이 없으면 쓰지 않는다.
- "왜 X를 쓰는가"처럼 기존 방식과 비교하는 글은 기존 방식의 불편함과 X의 해결을 1대1로 짝짓는다. 해결 소제목은 첫 문장에서 어떤 불편함을 푸는지 다시 짚고 시작한다.
- 비교형 글은 X를 소개하는 소제목에 같은 일을 하는 기존 코드와 X 코드를 before, after로 한 코드 블록에 나란히 둔다. before 코드의 주석에는 그 줄이 몇째 불편함에 해당하는지 적는다.
- 비교형 글에서 불편함을 들 때는 기존 도구로 직접 풀 수 있는 방법(예: 디바운스 훅 직접 작성)도 짚고, 그렇게 해도 남는 비용을 X를 쓰는 근거로 든다.
- 끝에 "정리" 소제목을 둔다. 기준 버전이나 확인하지 못한 내용을 모은 소제목은 따로 두지 않는다.


[글 정리 방식]
- 엮는 개념은 제목의 질문을 이해하는 데 필요한 것만 넣는다. 질문에 답하는 데 필요 없는 곁가지(약점·예외·내부 구현)는 넣지 않고, 꼭 필요하면 배경 설명과 함께 넣는다.
- 같은 내용을 두 번 설명하지 않는다. 같은 개념에 예제를 여러 개 겹쳐 쓰지 않는다.
- 처음 배우는 사람이 바로 그려지지 않는 주장에는 짧은 예시나 코드 스니펫을 붙인다.
- 의사 코드는 쓰지 않는다.
- 문장은 평이하게 쓴다. "A가 아니라 B다" 구문, 비유, "~라는 점이다" 같은 상투구를 쓰지 않는다.
- 소제목 끝에 다음 소제목으로 넘어가기 위한 문장을 따로 만들지 않는다. "남은 물음은", "이제 ~할 수 있다" 같은 다리 문장도 쓰지 않는다.
- 추상적인 말 대신 코드에 나온 이름과 구체적인 예를 쓴다. "맡긴다", "처리한다"에는 누구에게, 무엇을 하는지 적는다.
- 문장은 간결하고 명확하게, 한 문장에 하나의 개념만 담는다. 다만 주장에 붙는 조건은 그 주장과 같은 문장에 둔다.
- 앞뒤 문장에 원인과 결과가 실제로 있을 때만 "그래서"처럼 인과로 잇는다. 나란한 사실은 나란히 쓰고, 없는 인과를 만들지 않는다.
- 같은 대상은 한 가지 이름으로만 부른다. 새 용어는 처음 나올 때 한 문장으로 설명한다.
- 실행 결과에는 각 줄이 언제 출력되는지 적는다.


[그림]
- 그림은 처음 쓸 때 넣지 않는다. 사용자가 글을 보고 요청하면 2차로 넣는다.
- 그림 하나는 본문 문장 하나가 말하는 구조나 흐름만 그리고, 그 번호 항목의 자식 블록으로 넣는다.
- 그림 안의 숫자, 결과, 문구도 [근거 자료] 규칙을 따른다. 측정하지 않은 값을 넣었다면 그림 안에 예시라고 적는다.
- scratchpad의 이번 그림 전용 폴더(`study-writing-fig-<YYYYMMDD-HHMM>/`)에 HTML로 그린 뒤 Chrome 헤드리스로 2배율 PNG를 뽑는다. 뽑은 PNG는 직접 열어 잘림과 어색한 줄바꿈이 없는지 확인한다.
    ```sh
    "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --disable-gpu --hide-scrollbars --force-device-scale-factor=2 --window-size=1200,<높이> --screenshot=<이름>.png "file://<경로>/<이름>.html"
    ```
- 노션에는 `notion-create-file-upload`로 업로드 주소를 받아 `curl`로 PNG를 올린 뒤, `<image src="file-upload://<id>"></image>`로 넣는다.
- 그림 전용 폴더는 그림 수정이 끝날 때까지 둔다. 사용자가 "정리 끝"이라고 하면 노션 페이지를 fetch해 그림이 모두 이미지 블록으로 들어갔는지 확인한 뒤 폴더를 지운다.
- 이미지가 든 줄은 `update_content`의 부분 치환에 매칭되지 않는다. 이미지를 바꾸거나 옮길 때는 `replace_content`로 페이지 전체를 쓰고, 그대로 둘 이미지는 fetch로 받은 `notion-file-block://` 주소를 그대로 옮긴다.
- 사용자가 그림 모양을 여러 안 중에서 고르고 싶다고 하면 design-helper 스킬로 시안을 나란히 보여 준다.


[근거 자료]
- 사실 관계는 공식 문서, 언어나 프로토콜 명세, 라이브러리 소스 코드 같은 1차 자료를 기준으로 한다. 웹 검색을 쓸 수 있으면 글을 쓰기 전에 해당 자료를 먼저 확인한다.
- 개인 블로그나 Q&A 글은 1차 자료에서 답을 찾지 못했을 때만 보조로 참고하고, 1차 자료와 내용이 다르면 1차 자료를 따른다.
- 버전에 따라 달라지는 내용은 그 문장 안에서 어느 버전 기준인지 밝힌다.
- 자료에서 확인하지 못한 내용은 확인하지 못했다고 밝히고, 추측을 사실처럼 쓰지 않는다.
- 요청 횟수, 출력, 실행 순서 같은 관찰 결과는 직접 실행해 확인한 값만 쓴다. 실행하지 않았으면 "~할 수 있다"로 쓴다.
- 소스나 문서를 요약할 때 옵션이나 버전에 따라 갈리는 조건을 빼지 않는다. 기본값에서만 맞는 문장이면 기본값 기준이라고 밝힌다.
- 효과를 부풀리거나 조건 없이 단정하지 않는다. 다른 도구로도 되는 일을 그 라이브러리만의 장점처럼 쓰지 않는다.


[자료를 쓰는 방식]
- 자료는 사실을 확인하는 용도로만 쓰고, 글은 새로 쓴다. 블로그 글은 사용자 자신의 글이어야 하고, 문서를 옮겨 적은 문장은 번역투가 되어 읽기 어렵기 때문이다.
- 문서의 문장, 설명 순서, 예시 코드를 그대로 가져오지 않는다. 내용을 이해한 뒤 [글 구성]의 순서에 맞춰 다시 구성하고, 같은 원리를 보여주는 예시를 새로 만든다.
- API 이름과 공식 용어는 바꾸지 않고 그대로 쓴다.


[출력 포맷]
- 소제목은 ## 형태로 작성한다.
- 소제목, 본문 어디에서도 줄표 문자(em dash, U+2014)를 사용하지 않는다. ":", "->" 같은 문자를 사용한다.
- 모든 내용은 한 문장씩 끊어서 번호를 붙인다. (1. 2. 3. …). 소제목마다 새로 시작하고, 소제목과 공식 사이트·저장소 링크 줄에는 번호를 붙이지 않는다.
- 소제목 ##와 맨 위 설명 인용 블록 외에 볼드 등의 추가 포맷은 사용하지 않는다.
- 코드가 필요한 경우 코드 블록을 문장 사이에 자연스럽게 삽입한다.
    - 이때 코드 스니펫은 원리를 이해하는 데 필요한 로직만 적는다. 예를 들어 구체적인 스타일이 필요 없다면 뺀다.
    - 코드 스니펫 안에는 반드시 주석으로 설명을 단다. 핵심 줄마다 그 줄이 무엇을 하는지, 왜 필요한지 적는다.
- 학습 글은 "~이다.", "~한다."와 같은 해라체로 고정한다.
- 파일명, 함수명, 변수명, 키워드, API 이름 등 코드 문법에 해당하는 용어는 인라인 코드(백틱 `)로 감싸서 표기한다.
- 번호 리스트 항목 아래에 코드 블록을 둘 때는, 코드 블록 전체(여는 ```부터 닫는 ```까지 모든 줄)를 4칸 들여쓰기해서 직전 항목의 자식 블록이 되도록 작성한다. 그래야 리스트 번호가 끊기지 않고 연속된다.
