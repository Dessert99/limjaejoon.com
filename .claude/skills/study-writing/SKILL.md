---
name: study-writing
description: 기술 개념을 학습용으로 설명하거나 블로그 글 초안을 쓸 때 따르는 글쓰기 규칙. 사용자가 노션에 적은 목적과 목차를 채우고, 1차 자료로 사실을 확인하며, 문장마다 번호를 붙이고 해라체와 고정된 출력 포맷을 지킨다. 사용자가 "공부하게 정리해줘", "학습용으로 정리", "블로그 글로 써줘", "study-writing" 같은 말로 기술 개념을 학습 글로 정리해 달라고 할 때 쓴다. 코딩 중에 나온 일반 질문에 답할 때는 쓰지 않는다.
---

학습 글은 아래 규칙을 따른다. 작업 진행이나 반영 결과를 채팅으로 보고할 때는 [출력 포맷]을 따르지 않는다.
초안을 쓴 뒤 사용자 피드백을 반영할 때도 매번 이 스킬의 규칙과 작업 순서를 그대로 따른다. 단, Codex 재검토는 [작업 순서]에 적힌 조건일 때만 한다.

[정리 위치]
- 정리한 글은 사용자가 주는 노션 링크의 페이지에 쓴다.
- 링크를 받기 전에는 노션 페이지를 새로 만들지 않고, 사용자에게 링크를 요청한다.


[작업 순서]
- 목차대로 초안을 scratchpad의 이번 글 전용 폴더(`study-writing-<YYYYMMDD-HHMM>/`)에 마크다운 파일로 먼저 쓰고, 초안의 주장을 1차 자료로 확인한다. 노션에는 아직 쓰지 않는다.
- 초안을 Codex에게 넘겨 피드백을 받는다. 반영한 뒤 같은 초안을 다시 넘기지 않는다. ChatGPT 구독의 사용량 한도 때문이다.
- 사용자 피드백으로 구조를 크게 바꿨을 때는 노션에 쓰기 전에 고친 본문을 Codex에게 한 번 더 넘긴다. 소제목을 더하거나 빼거나 순서를 바꾼 경우, 한 소제목의 절반 이상을 새로 쓴 경우가 여기에 해당한다.
- 지적마다 반영과 보류를 정한다. 사실 지적은 1차 자료로 다시 확인한 뒤 반영하고, 근거가 약하거나 취향 차이인 지적은 보류한다.
- 문체와 출력 포맷은 Codex에게 맡기지 않고, 이 스킬 규칙과 대조해 직접 점검한다.
- Codex에 넘기기 전에 [번호 흐름]의 점검을 먼저 하고, 걸린 구간을 다시 쓴다.
- 최종본을 노션에 한 번에 쓰고, 이번 글 전용 폴더를 지운다.
- 채팅에는 반영한 지적과 보류한 지적을 이유와 함께 짧게 보고한다.
- Codex 실행이 실패하면(로그아웃, 네트워크) 피드백 없이 진행하고, 보고에 그 사실을 적는다.
- 사용자가 노션 본문 중간에 남긴 피드백 블록은 하나씩 반영하고, 반영한 블록은 지운다. 반영하지 않은 블록이 있으면 이유를 보고한다.
- 피드백을 반영한 뒤에는 고친 소제목 전체를 처음부터 다시 읽어 [번호 흐름]을 점검하고, 바뀐 용어·전제·내용이 다른 소제목과 겹치거나 어긋나지 않는지 글 전체에서 확인한다.
- 정확성에 필요한 문장을 지우라는 요청을 받으면, 지우기 전에 이유를 말하고 더 분명한 문장을 제안한다.
- 사용자가 본문 내용을 질문하면 1차 자료나 실행으로 확인한 뒤 답하고, 그 질문이 글을 읽다 막힌 지점이면 반영할 문장을 함께 제안한다.


[Codex 피드백]
- 프롬프트 파일에 아래 지시, 목적, 제목, 초안을 차례로 넣고, 저장소 루트에서 읽기 전용으로 실행한다.
    ```sh
    codex exec -s read-only --ephemeral -o <폴더>/codex.md - < <폴더>/prompt.md
    ```
- 그림을 넣은 차례에는 PNG를 `-i <파일>`로 모두 붙이고, 초안에서 그림이 들어갈 번호 항목 아래에 `[그림: <파일명>]`을 적어 어느 문장의 그림인지 알게 한다.
- 프롬프트 지시는 아래 내용을 그대로 쓴다. 스킬 전체는 넘기지 않는다. 문체 지적이 섞이면 사실 지적이 묻히기 때문이다.
    ```text
    너는 기술 학습 글의 검토자다. 목차는 글쓴이가 정했으니 소제목을 더하거나 빼거나 옮기라고 하지 않는다.
    아래에 적힌 글의 목적을 기준으로, 그 목적에 크게 어긋나는 것만 찾는다. 오개념과 앞에서 세우지 않은 전제에 기대 읽다가 막히는 문장이 여기에 해당한다.
    글의 목적과 상관없는 예외나 엄밀성을 따지는 지적은 하지 않는다.
    그림이 첨부되어 있으면 그림도 같은 기준으로 본다.
    문체, 맞춤법, 출력 포맷은 지적하지 않는다. 글을 고쳐 쓰지 않는다.
    지적마다 위치(소제목, 번호), 문제, 근거, 고칠 방향, 확신도(높음/중간/낮음)를 적는다.
    문제가 없으면 "지적 없음"이라고만 답한다.
    ```


[제목과 설명]
- 제목은 노션 페이지 제목으로 쓴다. 검색어 + 글이 답하는 내용 순서로, 기술 이름을 앞에 두고 35자 안팎으로 쓴다.
- 설명은 목적 줄 바로 아래에 인용 블록(`>`)으로 넣는다.
- 설명만 읽고 멈춘 사람도 제목의 답을 가져가게 쓴다. 제목이 질문 꼴이 아니어도 제목이 다루는 것 전부에 답하고, 동작 원리나 본문 요약을 쓰지 않는다.
- 설명은 본문보다 먼저 읽히므로 본문에서 처음 설명하는 용어를 쓰지 않는다. 조건은 결론이 뒤집히는 것만 남긴다.
- 글이 다루는 라이브러리나 도구의 공식 사이트와 저장소 링크는 그것을 소개하는 소제목 바로 아래에 넣는다. 링크 글자는 "공식 사이트", "GitHub"처럼 줄이지 않고 전체 URL을 그대로 보이게 쓴다. 이 줄에는 번호를 붙이지 않는다.
- 설명에는 「~를 다룬다」, 「~를 정리한다」, 「~를 기준으로」 같은 범위·기준 소개를 쓰지 않는다.


[글 구성]
- 글은 사용자가 잡아 준 목차(소제목과 순서)를 뼈대로, 사용자가 노션에 `- 목적:`으로 적은 목적을 이루도록 채운다. 목적이 없으면 쓰기 전에 요청한다.
- 목적만 있고 목차가 없으면, 목적에 맞는 목차를 채팅으로 제안하고 사용자가 정한 뒤에 쓴다.
- 글의 목적은 따로 짐작하지 않고 사용자가 적은 목적을 따른다. 그 목적을 더 잘 이루는 방법이 있을 때만 소제목의 뜻이나 순서를 바꾸거나 소제목을 더하거나 뺀다.
- 목적 줄은 본문이 아니므로 번호를 붙이지 않고, 최종본을 쓸 때도 지우지 않고 그대로 둔다.
- 목차를 바꿨으면 채팅 보고에 무엇을 왜 바꿨는지 적는다.
- 소제목 안의 번호 문장은 그 소제목이 답할 내용을 향해 쌓는다. 각 문장은 앞 문장까지 읽은 사람이 다음에 알아야 할 것을 말한다.
- 문장이 기대는 전제는 그 문장보다 앞에서 세운다. 이어 보이게 하려고 접속어를 붙이지 않는다. 내용이 이어지면 문장은 접속어 없이도 이어진다.
- 주장에 이유를 댈 때는 자료나 소스에서 확인한 한 층 아래의 구조로 받친다.
- 동작이나 개념을 설명한 소제목은, 그것이 글의 목적에 왜 필요한지가 본문에 드러나지 않으면 독자가 언제 무엇을 얻거나 잃는지를 덧붙인다.
- 장점을 단정할 때는 그 장점이 사라지거나 뒤집히는 조건이 있는지 확인하고, 있으면 그 조건을 같은 문장에 둔다.
- "왜 X를 쓰는가"처럼 기존 방식과 비교하는 글에서 해결 소제목은 첫 문장에서 기존 방식의 어떤 불편함을 푸는지 다시 짚고 시작한다.
- 비교형 글은 X를 소개하는 소제목에 같은 일을 하는 기존 코드와 X 코드를 before, after로 한 코드 블록에 나란히 둔다. before 코드의 주석에는 그 줄이 몇째 불편함에 해당하는지 적는다.


[번호 흐름]
- 번호 사이의 흐름은 참고 글 https://blog.naver.com/ranto28/224447237450 을 따른다. 말투(「~음」, 「~것임」), 소재(금융), 글을 몇 덩어리로 나눴는지는 따르지 않고, 문장과 문장이 어떤 관계로 이어지는지만 본다.
- 참고 글은 WebFetch로 열리지 않으므로 아래 명령으로 본문을 뽑아 읽는다. 쓰기 전에 매번 읽는다.
    ```sh
    curl -sL -A "Mozilla/5.0" "https://blog.naver.com/PostView.naver?blogId=ranto28&logNo=224447237450" | python3 -I -c "import sys,re,html;[print(s) for p in re.findall(r'<p[^>]*class=\"se-text-paragraph[^\"]*\"[^>]*>(.*?)</p>',sys.stdin.read(),re.S) if (s:=html.unescape(re.sub(r'<[^>]+>','',p)).strip().strip(chr(0x200b)))]"
    ```
- 글은 두 층으로 흐른다. 글 전체의 주제 아래 소제목들이 흐름을 나눠 맡고, 소제목 안의 번호들은 그 소제목이 맡은 몫을 향해 시작, 전개, 전환, 정리로 이어진다. 소제목끼리 내용으로 잇는 것은 흐름에 도움이 될 때만 한다.
- 다음 번호는 앞 번호와 관계를 맺는다. 앞 번호를 풀어 설명하거나, 이유와 근거로 뒷받침하거나, 앞 번호가 낳은 결과와 대가를 말하거나, 앞 번호에 처음 나온 대상을 소개한다.
- 처음 나온 대상은 다음 번호에서 무엇인지 소개하고, 그 대상이 앞 번호에서 왜 그렇게 하는지 이유까지 잇는다.
- 장점이나 결과를 말한 번호 뒤에는, 그것이 독자에게 실제로 무슨 뜻인지 한 겹 풀어 주는 번호를 둔다. 이미 드러나 있으면 두지 않는다.
- 초안을 다 쓰면 번호마다 앞 번호와 어떤 관계(설명, 뒷받침, 결과, 소개)인지 짚어 본다. 관계를 댈 수 없이 새 주어로 새로 시작하는 번호는 나열이므로 다시 쓴다.


[글 정리 방식]
- 문장마다 빼도 독자의 이해나 판단이 달라지지 않는지 따져 보고, 달라지지 않으면 뺀다. 꼭 필요하면 배경 설명과 함께 넣는다.
- 같은 내용을 두 번 설명하지 않는다. 같은 개념에 예제를 여러 개 겹쳐 쓰지 않는다. 앞에서 설명한 내용을 다시 보여 주는 소제목이나 그림도 만들지 않는다.
- 예외를 붙여야 하는 주장은 예외가 생기는 구조를 앞에서 세우거나, 그럴 가치가 없으면 주장의 범위를 줄여 예외가 필요 없게 한다.
- 처음 배우는 사람이 바로 그려지지 않는 주장에는 짧은 예시나 코드 스니펫을 붙인다.
- 의사 코드는 쓰지 않는다.
- 문장은 평이하게 쓴다. "A가 아니라 B다" 구문, 비유, "~라는 점이다" 같은 상투구를 쓰지 않는다.
- 소제목 끝에 다음 소제목으로 넘어가기 위한 문장을 따로 만들지 않는다. "남은 물음은", "이제 ~할 수 있다" 같은 다리 문장도 쓰지 않는다.
- 추상적인 말 대신 코드에 나온 이름과 구체적인 예를 쓴다. "맡긴다", "처리한다"에는 누구에게, 무엇을 하는지 적는다.
- 문장은 간결하고 명확하게, 한 문장에 하나의 개념만 담는다. 다만 주장에 붙는 조건은 그 주장과 같은 문장에 둔다.
- 앞뒤 문장에 원인과 결과가 실제로 있을 때만 "그래서"처럼 인과로 잇는다. 나란한 사실은 나란히 쓰고, 없는 인과를 만들지 않는다.
- 같은 대상은 한 가지 이름으로만 부른다. 새 용어는 처음 나올 때 한 문장으로 설명한다.
- 실행 결과에는 각 줄이 언제 출력되는지 적는다.


[그림]
- 그림은 처음 쓸 때 넣지 않는다. 사용자가 글을 보고 요청하면 2차로 넣는다.
- 그림 하나는 본문 문장 하나가 말하는 구조나 흐름만 그리고, 그 번호 항목의 자식 블록으로 넣는다.
- 그림 안의 숫자, 결과, 문구도 [근거 자료] 규칙을 따른다. 측정하지 않은 값을 넣었다면 그림 안에 예시라고 적는다.
- scratchpad의 이번 그림 전용 폴더(`study-writing-fig-<YYYYMMDD-HHMM>/`)에 HTML로 그린 뒤 Chrome 헤드리스로 2배율 PNG를 뽑는다. 뽑은 PNG는 직접 열어 잘림과 어색한 줄바꿈이 없는지 확인한다.
    ```sh
    "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --disable-gpu --hide-scrollbars --force-device-scale-factor=2 --window-size=1200,<높이> --screenshot=<이름>.png "file://<경로>/<이름>.html"
    ```
- 노션에는 `notion-create-file-upload`로 업로드 주소를 받아 `curl`로 PNG를 올린 뒤, `<image src="file-upload://<id>"></image>`로 넣는다.
- 그림 전용 폴더는 그림 수정이 끝날 때까지 둔다. 사용자가 "정리 끝"이라고 하면 노션 페이지를 fetch해 그림이 모두 이미지 블록으로 들어갔는지 확인한 뒤 폴더를 지운다.
- 이미지가 든 줄은 `update_content`의 부분 치환에 매칭되지 않는다. 이미지를 바꾸거나 옮길 때는 `replace_content`로 페이지 전체를 쓰고, 그대로 둘 이미지는 fetch로 받은 `notion-file-block://` 주소를 그대로 옮긴다.
- 사용자가 그림 모양을 여러 안 중에서 고르고 싶다고 하면 design-helper 스킬로 시안을 나란히 보여 준다.


[근거 자료]
- 사실 관계는 공식 문서, 언어나 프로토콜 명세, 라이브러리 소스 코드 같은 1차 자료를 기준으로 한다.
- 개인 블로그나 Q&A 글은 1차 자료에서 답을 찾지 못했을 때만 보조로 참고하고, 1차 자료와 내용이 다르면 1차 자료를 따른다.
- 글은 작성 시점의 최신 버전을 기준으로 쓰고, 본문에 마이너·패치 버전 번호를 적지 않는다. 메이저 버전에 따라 달라지는 내용만 메이저 버전으로 밝힌다.
- 자료에서 확인하지 못한 내용은 본문에 쓰지 않고, 확인하지 못했다는 언급도 하지 않는다.
- 요청 횟수, 출력, 실행 순서 같은 관찰 결과는 직접 실행해 확인한 값만 쓴다.
- 실행하지 않은 결과는 그 일이 일어나는 경로를 1차 자료로 확인했을 때만 "~할 수 있다"로 쓰고, 언제 무엇을 했을 때 일어나는지 같은 문장에 적는다. "~할 수 있다"를 확인하지 않은 주장의 면책 표현으로 쓰지 않는다.
- "흔하다", "자주", "대부분" 같은 빈도 표현은 1차 자료에 그 근거가 있을 때만 쓴다.
- 문장이 글에서 쓰는 설정과 버전에서 맞는지 확인한다. 기본값에서만 맞는 문장이면 기본값 기준이라고 밝힌다.
- 효과를 부풀리거나 조건 없이 단정하지 않는다. 다른 도구로도 되는 일을 그 라이브러리만의 장점처럼 쓰지 않는다.
- 기존 방식의 불편함도 같은 기준으로 쓴다. 독자가 이미 쓰는 장치나 우회 방법이 그 불편함을 얼마나 줄이는지 확인하고, 그래도 남는 부분만 불편함으로 쓴다. 비교하는 두 대상은 같은 상황에서 각각 어떻게 동작하는지 나란히 쓴다.


[자료를 쓰는 방식]
- 자료는 사실을 확인하는 용도로만 쓰고, 글은 새로 쓴다. 블로그 글은 사용자 자신의 글이어야 하고, 문서를 옮겨 적은 문장은 번역투가 되어 읽기 어렵기 때문이다.
- 자료에 있다는 이유로 목적 밖의 내용을 더하지 않는다.
- 본문에 "공식 문서에 따르면", "소스를 보면" 같은 출처 언급을 쓰지 않는다. 확인한 내용은 사실 그대로 쓴다.
- 직접 실행도 자료처럼 사실을 확인하는 데만 쓴다. 실험 환경, 실행 과정, "실험해 보니" 같은 서술은 본문에 쓰지 않고 확인한 사실만 쓴다.
- 문서의 문장, 설명 순서, 예시 코드를 그대로 가져오지 않는다. 내용을 이해한 뒤 목차에 맞춰 다시 구성하고, 같은 원리를 보여주는 예시를 새로 만든다.
- API 이름과 공식 용어는 바꾸지 않고 그대로 쓴다.


[출력 포맷]
- 소제목은 ## 형태로 작성한다.
- 소제목, 본문 어디에서도 줄표 문자(em dash, U+2014)를 사용하지 않는다. ":", "->" 같은 문자를 사용한다.
- 모든 내용은 한 문장씩 끊어서 번호를 붙인다. (1. 2. 3. …). 소제목마다 새로 시작하고, 소제목과 공식 사이트·저장소 링크 줄에는 번호를 붙이지 않는다.
- 소제목 ##와 설명 인용 블록 외에 볼드 등의 추가 포맷은 사용하지 않는다.
- 코드가 필요한 경우 코드 블록을 문장 사이에 자연스럽게 삽입한다.
    - 이때 코드 스니펫은 원리를 이해하는 데 필요한 로직만 적는다.
    - 코드 스니펫 안에는 반드시 주석으로 설명을 단다. 핵심 줄마다 그 줄이 무엇을 하는지, 왜 필요한지 적는다.
- 학습 글은 "~이다.", "~한다."와 같은 해라체로 고정한다.
- 파일명, 함수명, 변수명, 키워드, API 이름 등 코드 문법에 해당하는 용어는 인라인 코드(백틱 `)로 감싸서 표기한다.
- 번호 리스트 항목 아래에 코드 블록을 둘 때는, 코드 블록 전체(여는 ```부터 닫는 ```까지 모든 줄)를 4칸 들여쓰기해서 직전 항목의 자식 블록이 되도록 작성한다. 그래야 리스트 번호가 끊기지 않고 연속된다.
