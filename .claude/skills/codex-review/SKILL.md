# Codex 코드리뷰 받고 반영하기

Claude가 구현한 변경분을 **Codex CLI의 네이티브 리뷰 에이전트**(`codex review`)에 넘겨 리뷰받고, 타당한 피드백만 반영하는 스킬. Codex 자체 리뷰 능력을 그대로 쓰므로 커스텀 루브릭을 주입하지 않는다.

## 트리거 조건

- **명시적 호출:** 사용자가 "지금 변경사항 Codex/코덱스에게 리뷰(피드백) 받아봐", "코덱스 리뷰 돌려" 등으로 직접 요청할 때.
- **위임 호출:** 사용자가 긴 작업을 맡기며 "적절한 단위마다 / 2·5페이즈에 코덱스 피드백 받고 반영해" 식으로 체크포인트를 지정할 때. 이 경우 Claude가 작업을 진행하다가 해당 경계에서 **스스로** 이 스킬을 호출한다.

## 핵심 원칙

- **원샷.** 리뷰 → 반영 → 보고로 끝낸다. 반영 후 다시 Codex에 넘겨 재검증하는 루프는 돌리지 않는다. 사용자가 ChatGPT 구독 계정(사용량 한도 방식)을 쓰므로 체크포인트당 호출은 1회로 유지한다.
- **트리아지 후 반영.** Codex 지적을 무비판적으로 다 반영하지 않는다. 명백히 타당한 것만 반영하고, 애매하거나 이 프로젝트 맥락에 안 맞는 지적은 반영하지 않은 채 근거를 밝힌다.
- **리뷰는 읽기 전용.** `codex review`는 코드를 수정하지 않고 리뷰만 출력한다. 반영은 Claude가 직접 한다.
- **커밋·push 안 함.** 반영까지만 하고 커밋·push는 사용자 몫(레포 가드 정책).

## 절차

### Step 1: 리뷰 범위 결정

먼저 리뷰할 변경이 실제로 있는지 `git status --short` 로 확인한다. 없으면 그 사실을 알리고 종료한다.

범위별 명령:

- **기본 (미커밋 워킹트리):** `codex review --uncommitted` — 스테이징·미스테이징·untracked 전부. "지금 변경사항"의 기본값.
- **브랜치 전체:** `codex review --base main` — main 대비 브랜치 diff 전체.
- **특정 커밋:** `codex review --commit <sha>` — 그 커밋이 도입한 변경.

**위임 작업의 체크포인트에서는** 해당 페이즈 델타만 잡히도록 커밋 **전** 워킹트리를 리뷰한다(`--uncommitted`). 그 단위를 이미 커밋해 버렸다면 `--commit <sha>`로 그 커밋을 지정한다.

사용자가 특정 관점을 요청하면(예: "이번엔 성능만") 그 문구를 리뷰 지시로 전달한다: `codex review --uncommitted "성능 관점 위주로 봐줘"`. 특별한 요청이 없으면 프롬프트 없이 Codex의 종합 리뷰에 맡긴다.

### Step 2: 리뷰 실행

결정한 명령을 Bash로 실행하고 stdout(리뷰 결과)을 캡처한다. 리뷰는 에이전트가 도는 과정이라 수십 초 이상 걸릴 수 있다. 인증은 이미 `codex login`(ChatGPT 구독)으로 돼 있어 API 키가 필요 없다.

실행이 인증·네트워크 문제로 실패하면(예: `codex login status`가 로그아웃) 그 사실을 사용자에게 알리고 반영 없이 종료한다.

### Step 3: 트리아지

리뷰 결과의 각 지적을 분류한다:

- **반영** — 명백한 버그, 실제 회귀 위험, 프로젝트 컨벤션(FSD 레이어·TDD·주석 규칙·sprinkles 등) 위반처럼 근거가 분명한 것.
- **보류** — 취향 차이, 이 프로젝트가 의도적으로 택한 방식과 충돌, 지적이 코드 맥락을 오해한 것, YAGNI에 반하는 과잉 제안. 반영하지 않는다.

판단이 서지 않는 지적은 임의로 반영하지 말고 보류로 두고 보고 때 사용자에게 판단을 넘긴다.

### Step 4: 반영

반영으로 분류한 지적을 코드에 적용한다. 기존 코드 수정은 CLAUDE.md의 외과적 변경 원칙을 따른다 — 지적된 부분만 고치고 인접 코드를 임의로 손대지 않는다. 테스트가 있는 로직이면 반영 후 관련 테스트를 돌려 회귀가 없는지 확인한다.

### Step 5: 보고

사용자에게 요약한다:

- 리뷰 범위와 Codex가 낸 지적 수
- **반영한 항목** — 무엇을 왜 고쳤는지 (파일·근거)
- **보류한 항목** — 무엇을, 왜 반영하지 않았는지
- 판단이 필요한 항목이 있으면 사용자에게 질문

위임 작업 중이었다면 보고 후 원래 작업(다음 페이즈)을 자연스럽게 이어간다. 재검증 리뷰는 돌리지 않는다.
